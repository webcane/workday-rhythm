# Архитектура

Workday Rhythm использует модульный монолит: один процесс macOS и направленный граф SwiftPM targets. Стиль — функциональное ядро с императивной оболочкой. Предметные модели и переходы состояния отделены от UI, хранения и системных событий; координация связывает эти части. Полный Clean Architecture, универсальная шина событий и DI-контейнер для каркаса не нужны.

## Границы модулей

| Target | Ответственность | Разрешённые локальные зависимости |
|---|---|---|
| Program | Модели и проверка дневной программы | нет |
| TimerEngine | Состояния и чистые переходы с явным временем | Program |
| SettingsStore | Изоляция доступа к UserDefaults | Program |
| MacIntegration | Системные события и сигналы macOS | нет |
| SessionCoordinator | Последовательная обработка команд и вызов адаптеров | Program, TimerEngine, SettingsStore, MacIntegration |
| Presentation | Строка меню, окно настроек, маршрутизация UI-команд | SessionCoordinator |
| WorkdayRhythmApp | Создание зависимостей и жизненный цикл процесса | Presentation, SessionCoordinator, SettingsStore, MacIntegration |

Таблица задаёт разрешённые связи, а `Package.swift` — фактические зависимости. `Program` и `TimerEngine` могут импортировать только Foundation и разрешённые локальные модули. `Presentation` не обращается напрямую к ядру таймера или хранилищу. Изменение границ требует согласованного изменения архитектурного решения, manifest и правил в `ArchitectureTests`.

## Текущие типы и владение

- `WorkdayRhythmApp.main()` — единственная точка входа и composition root. Создаёт `SettingsStore`, `MacIntegration`, `SessionCoordinator`, `AppShell`; переводит `NSApplication` в accessory-режим и запускает event loop.
- `SessionCoordinator` хранит `TimerEngine`, `SettingsStore` и `MacIntegration`. Сейчас это только связывание компонентов; команды реального таймера отсутствуют.
- `AppShell` реализует `NSApplicationDelegate`. Точка входа удерживает его через `withExtendedLifetime`, поскольку `NSApplication.delegate` не обеспечивает необходимое владение.
- `AppShell` удерживает один `NSStatusItem` и лениво создаваемый `NSWindow`. Окно не освобождается при закрытии, поэтому повторное открытие использует тот же экземпляр. Закрытие окна не завершает приложение.
- Команда «Настройки» открывает окно; «Выход» вызывает `NSApplication.terminate`. При завершении статусный элемент удаляется.
- `ProgramModule`, `TimerEngine` и `MacIntegration` пока являются минимальными заглушками. `SettingsStore` удерживает UserDefaults, но ничего не читает и не сохраняет.

## Правила проектирования

**Изоляция.** `AppShell`, точка входа, `SessionCoordinator` и владельцы адаптеров изолированы `@MainActor`. Новые команды координатора обрабатывайте последовательно. Ядро не должно зависеть от главного потока; переносимые значения оформляйте как `Sendable`, когда они пересекают границу изоляции. Не используйте `@unchecked Sendable` для обхода ошибок конкурентности.

**Внедрение зависимостей.** Передавайте зависимости через initializer и удерживайте их явно. Избегайте singleton и service locator в прикладном коде. Системные объекты AppKit допустимы в оболочке; UserDefaults доступен только через SettingsStore. Протокол вводится при появлении необходимой границы или заменяемой зависимости, без создания протокола для каждого типа.

**Данные и эффекты.** Будущие переходы таймера должны получать время и входное событие явно и возвращать состояние/эффекты. Чтение часов, ожидание, уведомления и хранение выполняются за границами ядра. Сейчас эти API и алгоритм дневного цикла ещё не реализованы.

**UI.** Presentation переводит события интерфейса в прикладные команды и отображает результат. Оно не рассчитывает интервалы программы и не сохраняет настройки. Системные действия открытия окна и выхода остаются в оболочке; для тестирования маршрутизации запланирована минимальная точка подстановки обработчиков.

**Расширение.** Добавляйте конкретный контракт под подтверждённый сценарий. Не вводите фиктивные команды, работающий «по умолчанию» таймер или сохранение сессии ради заполнения каркаса. Новое поведение должно соответствовать выбранному изменению OpenSpec.
