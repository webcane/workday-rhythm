# Тестирование

Тесты используют XCTest и запускаются без графического сеанса. Подготовка Xcode, команды запуска и решение ошибки `no such module 'XCTest'` находятся в [документе по разработке](development.md). Команды там служат единым источником для разработчика и агента.

## Организация и правила

- Размещайте проверки в `Tests/<Target>Tests/`, файлы называйте `UpperCamelCaseTests.swift`. Текущий target архитектурных проверок — `ArchitectureTests`.
- Методы XCTest называйте `test<Behavior>`. Название должно описывать поведение, assertions — наблюдаемый результат. Для обязательных значений используйте `XCTUnwrap`.
- Проверки ядра должны быть детерминированными: время и внешние эффекты передаются явно. Не используйте реальные ожидания для имитации рабочих интервалов.
- Изолируйте состояние тестов. Не обращайтесь к реальному профилю UserDefaults и не завершайте тестовый процесс обработчиком выхода приложения.
- Временные нарушения для отрицательных проверок вносите в копию пакета либо гарантированно восстанавливайте исходные файлы.

## Текущее автоматическое покрытие

В `Tests/ArchitectureTests/ArchitectureTests.swift` находятся три проверки:

| Проверка | Что подтверждает |
|---|---|
| `testPackageDependencies` | Фактический граф targets соответствует разрешённым границам; внешних пакетов нет |
| `testSourceImports` | Исходники не импортируют запрещённые модули и UI-фреймворки в ядре |
| `testCheckerRejectsForbiddenEdgesAndImports` | Правила обнаруживают подставленные запрещённые зависимости и импорты |

Источник правил — таблица в [архитектуре](architecture.md); исполняемая проверка находится в `ArchitectureTests`. При изменении границ обновляйте их согласованно.

Тесты не проверяют все правила архитектуры, владение ресурсами, наличие значка или поведение окна. Проверки маршрутизации команд «Настройки» и «Выход» ещё не реализованы и запланированы изменением `establish-test-foundation`. Автоматическое форматирование и CI относятся к `establish-swift-code-quality`.

## Ручная проверка оболочки

После запуска приложения по инструкции разработки:

1. Найдите значок Workday Rhythm в строке меню и откройте меню команд.
2. Выберите «Настройки»: должно открыться отдельное окно с русским текстом о будущих параметрах дневной программы.
3. Закройте окно. Приложение и значок должны остаться доступными.
4. Повторно выберите «Настройки»: окно должно открыться снова.
5. Выберите «Выход»: значок должен исчезнуть, процесс и команда запуска — завершиться.

Эта проверка требует графического сеанса macOS. Если агент не имеет доступа к интерфейсу, получите ручное подтверждение пользователя и укажите его отдельно от автоматических результатов.

## Результат проверки каркаса

16 ноября 2026 года с Xcode Swift 6.3.3: сборка и три архитектурных теста прошли. Временное добавление `Presentation → TimerEngine` и `import AppKit` в Program дало ожидаемые ошибки; исходные файлы восстановлены. Пользователь подтвердил весь ручной сценарий оболочки, команда запуска завершилась успешно. Доступ агента к интерфейсу не был разрешён.

После добавления проектного скрипта обычный запуск тестов через него также прошёл: три теста, ноль ошибок. Это результат проверки каркаса, а не подтверждение будущих изменений.
