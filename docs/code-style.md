# Стиль Swift

Эти соглашения действуют для `Package.swift`, `Sources/` и `Tests/`. Исполняемые правила находятся в корневом `.swift-format`; команды применения и проверки приведены в [инструкции разработки](development.md).

## Имена и файлы

- Английские ASCII-идентификаторы. Типы, протоколы и SwiftPM targets — `UpperCamelCase`; функции, свойства, параметры, локальные переменные и enum cases — `lowerCamelCase`. Правила идентификаторов проверяет `swift-format`.
- Имена описывают назначение: `settingsWindow`, `showSettings`, `SessionCoordinator`. Следуйте Swift API Design Guidelines: понятные имена и метки аргументов, без сокращений ради длины.
- Один основной тип на файл с именем типа, например `SessionCoordinator.swift` или `ProgramModule.swift`. Вспомогательные private-типы и extensions того же типа можно держать рядом.
- Файлы тестов называйте `UpperCamelCaseTests.swift`, например `MenuCommandsTests.swift`. Методы тестов и их поведение описаны в [тестировании](testing.md).
- Исключения для имён файлов: `Package.swift` и `main.swift` как точка входа executable target. Текущая точка входа названа `WorkdayRhythmApp.swift` по основному типу.
- Каталог target совпадает с его именем: `Sources/TimerEngine/`, `Tests/ArchitectureTests/`. Пути Swift-файлов проверяет `scripts/check-names.sh`; соответствие путей manifest проверяется сборкой SwiftPM.

## Оформление

- Четыре пробела, без табуляции; открывающая фигурная скобка на той же строке. Конечный перевод строки обязателен.
- Максимальная длина строки — 120 символов. Длинные списки аргументов, коллекции и вызовы переносите на несколько строк. В многострочных списках используйте завершающую запятую.
- Импорты размещайте в начале файла, по одному на строку, в алфавитном порядке. Отделяйте импорты от объявления пустой строкой.
- Пустая строка разделяет функции и смысловые группы свойств; не выравнивайте код пробелами в таблицы.
- Комментарии объясняют причину или границу ответственности. Документируйте назначение публичных контрактов через `///`.

## API и безопасность типов

- По умолчанию используйте `let` и минимальную видимость. Детали реализации — `private`; `public` — только для контракта между targets.
- Не используйте `try!` и force unwrap в обычном коде. Обрабатывайте отсутствие значения через `guard`, `if let` или осмысленное значение по умолчанию.
- Модели и снимки состояния оформляйте как value types (`struct`/`enum`). Классы используйте для владельцев ресурсов, ссылочной идентичности и жизненного цикла; закрывайте наследование через `final`, если оно не требуется.
- Не подавляйте ошибки без объяснения. Ожидаемые ошибки передавайте через явный результат либо `throws`; UI переводит их в понятный пользовательский текст.
- Публичные API не должны возвращать AppKit-типы из ядра. Правила изоляции и передачи зависимостей описаны в [архитектуре](architecture.md).

## Владение константами и правилами

У каждого значимого правила или набора вариантов должен быть один типизированный владелец, выбранный по смыслу значения:

| Вид значения | Владелец |
|---|---|
| Ограничение предметной модели | Тип модели или правил в доменном target |
| Временное ограничение эталонной UI-модели | Соответствующий тип draft-модели |
| Общая визуальная семантика | `DesignTokens` |
| Связанная геометрия одного компонента | Именованный `private enum Metrics` компонента |
| Настройка пользователя | `SettingsStore` |
| Параметр сборки или окружения | `.xcconfig` или системный механизм сборки |
| Независимое ожидаемое значение теста | Сам тест |

- Не создавайте общий `Constants`: он скрывает владельца и связывает значения только из-за совпадения литералов.
- Повторяющийся список вариантов храните у владельца правила и используйте один источник для отображения, навигации и проверки.
- Переносите значение в `DesignTokens` только при одинаковой визуальной семантике в нескольких компонентах. Случайно равные размеры с разным назначением остаются раздельными.
- Группируйте внутренние размеры, непрозрачности, пороги и длительности составного компонента в его `private enum Metrics`, если значения повторяются, участвуют в общей формуле или вместе задают контракт геометрии.
- Литерал допустим на месте использования, если он очевиден, используется однократно и не выражает самостоятельное правило: например, индекс, направление, тестовый вход или размер Preview.
- Ожидаемые значения теста записывайте независимо и явно. Не сравнивайте production-константу с ней самой: такой тест не обнаружит непреднамеренное изменение правила.
- Значения, которые меняются только с новой версией приложения, храните в коде. Во внешний ресурс или пользовательскую настройку выносите только параметры, которые действительно должны изменяться без пересборки.

При конфликте ручного оформления с результатом `swift-format` применяйте форматтер и обновляйте это соглашение вместе с конфигурацией.
