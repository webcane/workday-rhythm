# Design

## Context

Мотивация описана в proposal.md. В проекте уже реализованы модульный каркас, оболочка и предпросмотр настроек; дневной таймер и хранение программы ещё не подключены. Согласованные правила переходов находятся в specs/timer-cycle/spec.md.

## Goals / Non-Goals

**Goals:** единое состояние сессии, проверяемые переходы, независимость ядра от интерфейса и хранения.

**Non-Goals:** восстановление сессии после выхода, работа после выхода через отдельный процесс, история и синхронизация. Полный переход на `PlannedInterval`, редактируемая шкала расписания и индивидуальные названия интервалов относятся к отдельному будущему change.

## Decisions

### Принято: одна сессия в памяти

Выход завершает сессию без восстановления; настройки сохраняются. Сон не завершает сессию. Альтернатива — сохранять снимок сессии — отклонена согласно выбранному поведению выхода.

### Принято: явная машина состояний в ядре

Ядро получает состояние, событие и время, возвращает новое состояние и эффекты. Основные состояния: готовность, работа, пауза, отдых, ожидание подтверждения, завершение. Интерфейс не принимает самостоятельных решений о переходах. Независимые флаги в UI отклонены из-за противоречивых сочетаний; отдельная библиотека машины состояний пока не требуется.

### Принято: UserDefaults через SettingsStore

Небольшой набор настроек сохраняется в UserDefaults через SettingsStore встроенными средствами Swift без сторонних зависимостей. SettingsStore возвращает проверенную модель настроек; ядро таймера и интерфейс не обращаются к ключам UserDefaults напрямую. Сессия остаётся только в памяти.

Отдельный JSON-файл отклонён: ручное редактирование не требуется, а управление расположением, чтением и записью файла добавляет сложность. TOML потребовал бы дополнительной зависимости; база данных для текущего объёма настроек не обоснована.

### Принято: длительности по виду интервала и переопределения отдыха

`WorkdayIntervalKind` содержит `focus` и `rest`. `WorkdayDefaults` содержит `kind` и `durationMinutes`; программа хранит настройки по ключу вида и обеспечивает ровно одну допустимую настройку для каждого поддерживаемого вида. Длительность получается по ключу вида, без выбора между полями `focusDurationMinutes` и `restDurationMinutes`. Отсутствующий или повторяющийся вид является ошибкой модели; нулевая длительность вместо отсутствующего значения не подставляется.

`RestDurationOverride` содержит `afterFocusNumber` и `durationMinutes`. Допускаются до двух переопределений для разных положительных номеров завершённой работы. Длинный перерыв — отдых с индивидуальной длительностью, а не отдельный вид интервала. При наличии переопределения используется его длительность, иначе — общая длительность по виду. Изменение общей длительности отдыха не меняет индивидуальную длительность назначенного перерыва.

Пауза является состоянием сессии с фактически прошедшей длительностью. Она не входит в `WorkdayIntervalKind`, не имеет общей настроенной длительности и не входит в последовательность планируемых фокусирований и отдыха. При этом сохраняется отдельная нумерация пауз, требуемая спецификацией. История фактических интервалов сейчас не вводится.

Настройки, выбор эффективной длительности и расчёт окон принадлежат `Program` и `TimerEngine` согласно их ответственности. `Presentation` получает данные через `SessionCoordinator` и не импортирует модели ядра напрямую. Существующая форма может сохранять отдельные поля черновика; преобразование в проверенную модель выполняется на границе координатора.

### Принято: один владелец правил дневной программы

Диапазоны начала дня, длительностей работы, отдыха и длинного перерыва, шаг начала дня, допустимые длительности дня и предел числа переопределений принадлежат типизированному `DailyProgramRules` в `Program`. Проверка `DailyProgram` и чистые расчёты программы используют эти правила без повторения литералов.

`Presentation` не дублирует доменные диапазоны. `SessionCoordinator` преобразует их в независимый снимок для интерфейса, из которого форма и шкалы получают варианты, границы и шаги. Визуальные шаги, не являющиеся ограничением предметной модели, остаются у соответствующего UI-компонента.

### Принято: существующие границы модулей

Состав targets, разрешённые зависимости и владение определены в [архитектуре проекта](../../../docs/architecture.md). Изменение использует существующий каркас, без пересмотра его границ.

UI обращается к координатору; координатор использует ядро, хранилище и адаптеры macOS. Ядро не зависит от окон и хранения. Время передаётся явно для проверки сценариев без ожидания. Системный таймер инициирует пересчёт, а не служит накопительным счётчиком секунд.

### Критерии выбора

1. Корректность переходов при паузах, сне и завершении дня.
2. Проверяемость сценариев без реального ожидания и UI.
3. Однозначное завершение сессии при выходе.
4. Простота: один процесс, локальные данные, минимум зависимостей.
5. Независимое изменение интерфейса и правил таймера.

Варианты: логика внутри UI ускоряет прототип, но усложняет проверку переходов; независимое ядро поддерживает отдельные проверки; фоновый процесс добавляет сложность без требования продолжать день после выхода. Рекомендован один процесс с независимым ядром.

## Risks / Trade-offs

- Повторные события → переходы и эффекты должны учитывать текущее состояние; пропущенные эффекты не выдаются цепочкой.
- Аварийный выход → сессия теряется, поскольку снимок не сохраняется.
- Изменение системных часов и часового пояса → отделить измерение длительности от календарных границ и проверить оба типа событий.
- Изменение настроек во время сессии → применять проверенную модель одним событием с пересчётом текущего состояния и следующих окон.

## Migration Plan

Существующих пользовательских данных нет; перенос из JSON-файла не требуется. Сохранением настроек управляет UserDefaults через SettingsStore. Для отсутствующих значений использовать начальные настройки. Как техническое решение, некорректные сохранённые значения отклонять той же валидацией и заменять допустимыми начальными значениями.

## Уточнения реализации

Поведение определено спецификациями daily-program, timer-cycle и menu-bar-control. Завершение сессии и завершение процесса различаются. Состояние завершённого дня оставляет приложение в фоне без запуска рабочих таймеров. Новую программу пользователь запускает командой меню.

При сохранении настроек координатор передаёт ядру новую проверенную модель и текущее время. Модель хранит начало дня, базовую длительность 4, 6, 8 или 10 часов, общие длительности по виду и переопределения отдыха. Конец вычисляется как начало плюс базовая длительность плюс сумма разниц `override.durationMinutes - defaults[.rest].durationMinutes` для всех настроенных переопределений. Например, 09:00 + 8 часов + (60 − 20) минут = 17:40. Разница знаковая: переопределение 20 минут при общем отдыхе 35 минут сокращает день на 15 минут; равные длительности не меняют конец. Изменение общей длительности отдыха также пересчитывает конец дня. Пропуск не поместившегося перерыва не меняет эту формулу.

Накопленное время работы исключает паузы. Сокращение интервала ниже накопленного времени вызывает один актуальный переход в момент сохранения. Ожидание подтверждения сдвигает будущие окна, но не вычисленный конец дня. Перед каждым запуском проверяется полная длительность относительно вычисленного конца дня.

Для длительностей требуется источник времени, учитывающий сон и устойчивый к ручному переводу часов. Календарные границы рассчитываются отдельно по локальному календарю. События пробуждения, активности, изменения часов и часового пояса последовательно поступают координатору. Повторное событие не должно дублировать эффект или переход.

Границы targets и сборка реализованы изменением scaffold-macos-app-architecture. Проверки используют готовую основу establish-test-foundation. Окно настроек использует существующие компоненты establish-design-system и toolbar-панель «Рабочий день». Настраиваемые сигналы и будущая toolbar-панель «Сигналы» относятся к отдельному change `configure-timer-alerts`. Конкретные контракты берутся из реализованного каркаса.
