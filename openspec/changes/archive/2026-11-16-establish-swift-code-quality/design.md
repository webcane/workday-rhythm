# Design

## Context

См. [proposal.md](proposal.md). Репозиторий пока содержит только OpenSpec-артефакты. Изменение `scaffold-macos-app-architecture` определяет будущие `Package.swift`, `Sources/<Target>/` и `Tests/`, но ещё не применено. В локальной среде Swift 6.3.2 предоставляет `swift format format` и `swift format lint --strict`; `just` не установлен.

## Goals / Non-Goals

**Goals:** один локальный вход для проверки качества Swift-кода; одинаковый набор локальных и CI-проверок; явные правила для идентификаторов, файлов и targets; ошибка проверки при нарушении правил.

**Non-Goals:** изменение поведения таймера, автоматическое исправление кода в CI, форматирование OpenSpec Markdown, релизная упаковка приложения.

## Decisions

### Встроенный `swift-format` для форматирования и линтинга

Хранить правила в корневом `.swift-format` и применять к `Package.swift`, `Sources/` и `Tests/`. Включить правила `AlwaysUseLowerCamelCase`, `TypeNamesShouldBeCapitalized` и `IdentifiersMustBeASCII`; задать отступ, длину строки и порядок импортов. `just fmt` запускает `swift format format --in-place --recursive` для исправления Swift-файлов. `just lint` запускает `swift format lint --strict --recursive` для проверки, включая пробелы и стиль имён; предупреждения должны давать ненулевой код завершения. Перед применением проверить флаги на выбранной версии Swift.

Один инструмент устраняет расхождение между форматтером и линтером. Отдельный SwiftLint рассматривался, но добавляет второй набор правил и установку внешней зависимости без текущей необходимости. Если позже понадобятся правила, которых нет в `swift-format`, его можно добавить отдельным изменением.

### Соглашения об именовании

Документировать в `docs/code-style.md`: английские ASCII-идентификаторы; `UpperCamelCase` для типов, протоколов и SwiftPM targets; `lowerCamelCase` для функций, свойств, параметров и enum cases; читаемые аббревиатуры в соответствии с правилами Swift API Design Guidelines; один основной тип на файл `UpperCamelCase.swift`; файлы тестов `UpperCamelCaseTests.swift`; исключения `Package.swift` и `main.swift`. Названия папок targets совпадают с именами targets в `Package.swift`. Правила идентификаторов проверяет `swift-format`; отдельный небольшой `scripts/check-names.sh` проверяет соглашения о путях Swift-файлов и выдаёт понятную ошибку. Он должен работать и в пустых `Sources/` или `Tests/` без ложного успеха всей проверки.

Рассматривались только текстовые соглашения, но они не предотвращают расхождение файловых имён между модулями. Полный парсер `Package.swift` для контроля структуры не нужен: корректность target-путей уже проверяет `swift build`.

### `just` как единый интерфейс команд

`justfile` описывает `fmt`, `lint`, `names`, `build`, `test` и `check`. `check` последовательно вызывает `lint`, `names`, `build`, `test` и прекращается при первой ошибке. Ни одна из этих проверок не меняет исходники; `fmt` запускается разработчиком отдельно. Все рецепты работают из корня репозитория. В `README.md` перечислить установку `just`, требуемую версию Swift и команды.

`just check` должен обнаруживать отсутствующий `Package.swift` и объяснять, что сначала нужен SwiftPM-каркас, вместо успешного пустого прогона. Так как каркас ещё не применён, реализацию этого изменения проводить после `scaffold-macos-app-architecture` либо вместе с ним. Альтернатива — набор команд в README без исполняемого интерфейса; она допускает расхождение локальной проверки и CI.

### CI выполняет проверки прямыми командами

Добавить workflow GitHub Actions на `pull_request` и `push` в `main` с macOS runner. Зафиксировать версию Xcode/Swift, совместимую с manifest каркаса и `.swift-format`. Отдельными шагами выполнить `swift format lint --strict --recursive Package.swift Sources Tests`, `./scripts/check-names.sh`, `swift build` и `swift test`. `just` остаётся локальным инструментом и не устанавливается в CI. При изменении проверок обновлять workflow и `justfile` вместе, чтобы их состав совпадал. Альтернатива — запуск `just check` в CI; она требует установки дополнительного инструмента на runner.

## Risks / Trade-offs

- Обновление Swift меняет диагностику `swift-format` → зафиксировать версию toolchain в CI и обновлять её вместе с конфигурацией.
- Локальный Swift может отличаться от CI → указать поддерживаемую версию в README и явно показывать версии в логе CI.
- Строгие правила имён могут затронуть системные имена или требуемые протоколом объявления → зафиксировать точечные исключения с объяснением, а не отключать правило глобально.
- Проверка путей может ошибочно принять пустой проект → `check` требует существующий `Package.swift`, а `build` и `test` завершаются с ошибкой без реального пакета.

## Migration Plan

Сначала применить SwiftPM-каркас, затем добавить конфигурацию и проверить исходные файлы; исправить найденные нарушения через `just fmt` и ручное переименование. После локального `just check` включить workflow. Откат — удалить добавленные файлы инструментов и CI; пользовательские данные не затрагиваются.
