# Design

## Context

В репозитории пока есть только OpenSpec-артефакты. Изменение [scaffold-macos-app-architecture](../scaffold-macos-app-architecture/design.md) задаёт будущий SwiftPM-пакет, граф targets и оболочку AppKit. Изменение [establish-swift-code-quality](../establish-swift-code-quality/design.md) определяет состав `just check`.

## Goals / Non-Goals

**Цель** — запускать из корня пакета детерминированные проверки каркаса без графического сеанса и пользовательского профиля настроек.

**Границы** — появление значка, открытие окна и завершение процесса проверяются вручную по сценарию каркаса. Реализация таймера относится к отдельному изменению.

## Decisions

### SwiftPM и XCTest

Использовать встроенный запуск `swift test` и XCTest из Swift toolchain. Зарегистрировать `PresentationTests` с прямой зависимостью от `Presentation` и разместить файлы в `Tests/PresentationTests/` по соглашению `UpperCamelCaseTests.swift`. Для архитектурных проверок использовать механизм, реализованный в задаче 2.2 каркаса, как единственный источник правил. Если он уже оформлен как test target, сохранить его имя и путь. Если он оформлен отдельной командой, включить её в запуск SwiftPM через тестовую обёртку, которая проверяет код завершения и показывает вывод при ошибке.

### Проверки каркаса

- Проверить фактический граф targets и ограничения на импорты средствами проверки каркаса. Во временной копии пакета убедиться, что отдельные нарушения, например ребро `Presentation → TimerEngine` и импорт AppKit в `TimerEngine`, дают ненулевой код завершения.
- Проверить, что команда «Настройки» вызывает открытие настроек ровно один раз, а обработчик выхода остаётся невызванным.
- Проверить, что команда «Выход» вызывает обработчик завершения ровно один раз, а обработчик настроек остаётся невызванным.

Тесты команд используют тот же маршрут, к которому привязаны пункты AppKit. Подставить локальные обработчики в существующую точку связывания. Если оболочка вызывает системные действия напрямую, выделить минимальную внутреннюю точку передачи обработчиков с сохранением обычных привязок при запуске приложения. Тесты запускают обработчики без создания статусного элемента, открытия окна и завершения тестового процесса.

### Команда проверки

Описать `swift test` в README как самостоятельный вход. В изменении качества рецепт `just test` вызывает ту же команду, а `just check` сохраняет уже запланированную последовательность. Если рецепты появятся раньше тестов, проверить их сквозной запуск после регистрации тестовых targets.

## Risks / Trade-offs

- Каркас ещё не реализован → начать работу после появления manifest, оболочки и архитектурной проверки. Имена конкретных типов брать из реализации.
- Тесты обработки команд покрывают маршрутизацию → проверку системного меню, жизненного цикла окна и выхода выполнить по ручным шагам каркаса.
