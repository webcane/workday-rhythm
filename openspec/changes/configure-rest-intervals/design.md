# Design

## Context

См. proposal.md. DailyProgram хранит массив RestDurationOverride, но ограничивает его двумя элементами и длительностью 20–240 минут. DailyProgramSettings передаёт форме только первый элемент и собирает максимум один; DailyProgramDraft и меню поддерживают одну позицию. LongBreakProjection принимает только один другой override. TimerEngine уже выбирает эффективную длительность по номеру отдыха и учитывает знаковую разницу в конце дня.

## Goals / Non-Goals

**Goals:** один список индивидуальных длительностей от хранения до формы; визуальная настройка выбранного отдыха и безопасный перенос старых программ.

**Non-Goals:** новый вид интервала для обеда, универсальный редактор любых этапов, история и перенос фактических пауз в номинальное расписание.

## Decisions

### Сохраняем модель переопределений

Расширить RestDurationOverride вместо введения отдельного вида «длинный перерыв». Номер завершённой работы остаётся идентичностью; час начала — вычисленное представление. Отдельный настраиваемый лимит числа назначений не нужен: список ограничен уникальными доступными отдыхами программы. Удаление возвращает общий default, значение, равное default, допустимо как явное индивидуальное назначение и не изменяется при последующем изменении общего значения.

Диапазон 5–240 минут принадлежит Program; UI предлагает шаг 5. Прежние допустимые целочисленные значения вне сетки UI сохраняются при миграции и отображаются точно до явного редактирования, без округления. Это важно, поскольку текущая доменная модель не ограничивает длительности шагом UI.

### Полный контракт формы

SessionCoordinator получает и возвращает весь список назначений. Черновик не восстанавливает коллекцию из одного выбранного элемента. Операции выбрать отдых, назначить длительность и вернуть default изменяют только нужный номер. Сохранение целиком валидирует программу до записи и применения. Ошибка не меняет действующую сессию.

До появления нового редактора сохранность второго назначения обеспечивается в build-scheduled-menu-bar-timer. Текущий UI одного перерыва не расширяется этим исправлением.

### Проекция выбранного отдыха

Обобщить чистую проекцию Program на весь список назначений и отдельную выбранную позицию, не ограничиваясь otherOverrides.count < 2. Выход содержит полные интервалы с видом, номером, началом, концом, эффективной длительностью и признаком индивидуальной настройки. Presentation использует независимые снимки координатора. Дублировать расчёт конца дня в SwiftUI не следует.

Каждое назначение должно соответствовать существующему отдыху. Для сохранения прежнего ограничения назначения после индивидуального отдыха должен помещаться следующий полный фокус; проверка выполняется по всему итоговому черновику. При этом сама последовательность включает каждый полный интервал отдельно и может заканчиваться фокусом или отдыхом. Не помещающийся назначенный отдых остаётся в черновике как ошибка, чтобы изменение другой длительности не приводило к потере данных.

Визуальный редактор использует последовательность выбираемых элементов с явными подписями. Выбор и редактирование доступны без мыши. Перетаскивание и масштабируемая временная линейка не обязательны для первой реализации: ключевое действие — выбрать конкретный отдых и задать его длительность.

### Defaults и миграция

Для новой программы использовать параметры текущей формы: обед 60 минут после №4. Сохранённый пустой список означает осознанную программу без обеда, а не отсутствие данных. Старые один или два override переводятся без смены номеров и длительностей. Схема чтения различает отсутствие программы, валидный пустой список и повреждённый payload. Расширение числа назначений требует проверки поведения старой версии при откате; старые версии могут отвергнуть новый список и показать initial, поэтому не обещать совместимость downgrade.

### Последовательность changes

Сначала опубликовать базы daily-program и long-break-time-options из текущих changes. Затем применять MODIFIED/REMOVED по тем же именам; не синхронизировать эту delta поверх отсутствующих баз. При изменении базы до реализации повторно сравнить все её сценарии. Требования старого меню удаляются только вместе с рабочим новым редактором.

## Risks / Trade-offs

- [Каскадная недоступность после изменения нескольких отдыхов] → валидировать весь итоговый черновик, показывать проблемные номера, не удалять назначения автоматически.
- [Смена default меняет явно равную индивидуальную длительность] → хранить факт назначения независимо от равенства значений.
- [Рост числа назначений] → гарантировать конечный расчёт в границах дня и проверять 0, 1, 2 и более двух назначений без переполнения.
- [Потеря информации при миграции] → round-trip старых payload, пустого списка, двух назначений и значений вне UI-сетки.

## Migration Plan

Расширить правила и чтение данных с тестами, затем снимки координатора и проекцию, после этого заменить меню редактором и убрать требования старого меню. До записи новой программы отмена оставляет старые настройки нетронутыми. Документировать ограничения отката версии в docs/development.md при реализации.
