# Design

## Context

См. мотивацию в `proposal.md`. В `Presentation` уже есть семантические `DesignTokens`, но часть общих размеров продублирована, а геометрия составных компонентов выражена связанными безымянными числами. Набор допустимой длительности дня одновременно используется для отображения, клавиатурной навигации и проверки в `DailyProgramView`.

Полная модель дневной программы запланирована изменением `build-scheduled-menu-bar-timer`, но ещё не реализована. Текущий `DailyProgramDraft` принадлежит эталонному интерфейсу, а архитектура запрещает прямую зависимость `Presentation` от `Program`. Этот change не должен преждевременно менять граф targets или реализовывать будущую модель программы.

## Goals / Non-Goals

**Goals:**

- разделить предметные правила, общие визуальные токены и локальную геометрию компонентов по явным владельцам;
- сохранить один источник значимых наборов и связанных параметров внутри текущей архитектуры;
- сделать назначение числовых литералов читаемым без создания глобального хранилища всех чисел;
- проверить модельные ограничения отдельно от SwiftUI-отрисовки.

**Non-Goals:**

- добавление внешнего JSON, plist, `.xcconfig` или пользовательской настройки для значений, которые меняются только вместе с кодом;
- реализация и сохранение полной дневной программы;
- изменение согласованных размеров, цветов, вариантов выбора или поведения интерфейса;
- запрет всех числовых литералов, включая очевидные индексы, направления, тестовые входы и независимые ожидаемые значения.

## Decisions

### Один владелец выбирается по смыслу, а не по совпадению литералов

В `docs/code-style.md` будет закреплена следующая матрица владения:

| Вид значения | Владелец |
|---|---|
| Ограничение предметной модели | Тип модели или правил в доменном target |
| Временное ограничение эталонной UI-модели | Соответствующий тип draft-модели |
| Общая визуальная семантика | `DesignTokens` |
| Связанная геометрия одного компонента | Именованный `private enum Metrics` компонента |
| Настройка пользователя | `SettingsStore` |
| Параметр сборки или окружения | `.xcconfig` либо системный механизм сборки |
| Независимое ожидаемое значение теста | Сам тест |

Одинаковые числа с разным смыслом не объединяются. Например, минимальная ширина содержимого секции и ширина popover могут обе быть равны 300 pt, но не образуют общий токен. Альтернатива с глобальным `Constants` отклонена: она скрывает владельцев и создаёт случайные связи.

### Допустимые длительности дня временно принадлежат `DailyProgramDraft`

До реализации `Program` набор 4, 6, 8 и 10 часов становится статическим именованным правилом `DailyProgramDraft`. `DailyProgramView` использует его для `ForEach`, клавиатурного перемещения, локальной ошибки и общей проверки. Текст ошибки формируется без независимого перечисления тех же значений.

Отдельные XCTest проверяют варианты, начальное значение и принятие каждого допустимого значения. После реализации `build-scheduled-menu-bar-timer` правило должно переехать в доменную модель `Program`, а UI — получить его через существующую прикладную границу. Прямая зависимость `Presentation → Program` в этом change не добавляется.

Альтернатива с немедленным enum в `Program` отклонена: её использование потребовало бы изменения согласованного графа модулей или дублирующего адаптера до появления самой предметной модели. Внешний ресурс отклонён, поскольку варианты не должны меняться без новой версии приложения.

### `DesignTokens` хранит только переиспользуемую визуальную семантику

Шкала пространства получает перечисляемое представление для каталога, чтобы `DesignSystemGallery` не повторял её числовой состав. Общие толщина тонкой линии и размеры, действительно используемые несколькими компонентами с одинаковым смыслом, получают семантические токены. Существующие роли цветов, типографики и радиуса сохраняются.

Токены не включают размеры Preview, тестовые размеры окна и внутреннюю геометрию одного контрола. Это предотвращает превращение `DesignTokens` в неструктурированный список констант.

### Геометрия составных компонентов группируется в локальные `Metrics`

`HorizontalRulerPicker` получает частный `Metrics` для расстояния между рисками, высоты контрола и рисок, ширины указателя, зон скрытия подписей, толщины границ, порога жеста, непрозрачности и длительности анимации. Формулы используют именованные зависимости, например зона вокруг центрального значения выражается через отдельную метрику, а не повторяется числом.

Тот же приём применяется к `RulerChevronButtonStyle`, `SettingsSection` и `SettingsWindow`, если в них есть несколько связанных или повторяемых параметров. Одноразовые очевидные значения не извлекаются автоматически.

Альтернатива с общими токенами для всей геометрии отклонена: параметры шкалы и шевронов являются внутренним контрактом компонентов, а не визуальным языком всего приложения.

### Проверки подтверждают правила, но не копируют реализацию

Модельные тесты проверяют наблюдаемые границы и значения по умолчанию. Ожидания в тестах остаются явными, даже если production-код имеет именованную константу: сравнение константы с ней самой не обнаруживает регрессию. Тестовые входы вроде расстояния перетаскивания 32 pt остаются локальными фикстурами, когда цель теста — проверить математику при переданном параметре.

`swift-format` не умеет обнаруживать семантические дубли. SwiftLint или собственный SwiftSyntax-анализатор в этом change не добавляется: правило проверяется структурой кода, тестами и review. Новый инструмент потребовал бы отдельного обоснования, установки и синхронного изменения локальной и CI-проверки.

## Risks / Trade-offs

- [Временный владелец вариантов дня останется в Presentation после появления доменной модели] → в документации и задачах явно зафиксировать последующую миграцию владельца в `Program` в рамках реализации дневной программы.
- [Извлечение каждого литерала ухудшит читаемость] → извлекать только значения с предметным смыслом, повторным использованием или связью с другими параметрами.
- [Тесты станут зависеть от деталей реализации] → проверять значения и поведение публичной внутренней модели, а не наличие конкретных имён `Metrics`.
- [Объединение случайно равных значений создаст ложную связь] → перед переносом в `DesignTokens` требовать одинаковую семантическую роль, а не только одинаковое число.

## Migration Plan

1. Добавить правила владения значениями в документ стиля.
2. Сосредоточить варианты длительности дня в `DailyProgramDraft` и добавить модельные тесты.
3. Устранить дубли шкалы пространства в каталоге дизайн-системы и выделить только общие визуальные токены.
4. Сгруппировать связанную геометрию компонентов в локальные `Metrics`, не меняя числовых значений.
5. Выполнить форматирование, полный `just check`, проверку diff и строгую валидацию change.

Откат выполняется удалением новых имён и возвратом литералов; миграция пользовательских данных не требуется.
